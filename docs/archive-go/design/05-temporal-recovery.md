# 5. Temporal and recovery design

**Status:** proposed; all timing values below are initial engineering settings to test, not approved performance/SLO thresholds. [Index](README.md).

**Implementation update:** the local core uses a real Temporal development server, persistent simulated effects, leased recovery tickets and version-gated legacy/new workflow replay. Process-loss/replay and selected failure cases passed; cancellation budgets, retry classification, history/Continue-As-New and the rest of the matrix remain acceptance work. Enterprise Temporal TLS/namespace authorization and ACA shutdown remain unverified. See [current evidence](12-verification.md#current-evidence-overlay).

The separate Key Vault spike has stable `forgeapi-deployment-<id>-plan` / `-apply` workflows on `forgeapi-local-key-vault`. Each invokes one bounded native Terraform activity (20-minute start-to-close, 25-minute schedule-to-close, one attempt); failed/uncertain apply requires operator recovery, not automatic replay/apply. This is a lab exception to the short compute activity model, not an implementation of the full future stack workflow. [ADR-0013](../adr/0013-local-terraform-lab-exception.md) preserves this distinction; compute rules below remain requirements for compute.

## Workflow and queue ownership

`ExecuteV1(execution_id, spec_digest, lifecycle_generation)` is the only initial workflow. Its input and activity outputs contain identifiers, hashes and sanitized outcomes. Activities fetch authorized immutable records; no command, full environment, credential, provider resource identifier, source content or raw provider response enters history. Provider references live in restricted PostgreSQL storage and are addressed by internal handle. Workflows cannot choose arbitrary target mappings or queue names from caller data.

Workflow identity: `execution/<execution_id>` in the assigned namespace. One stable identity spans Temporal runs, including Continue-As-New; `run_id` is not the business ID. Set Go start options `WorkflowIDConflictPolicy=WORKFLOW_ID_CONFLICT_POLICY_FAIL` and `WorkflowIDReusePolicy=WORKFLOW_ID_REUSE_POLICY_REJECT_DUPLICATE` (Temporal API enum values). A repeated external Start cannot replace an open workflow or restart a closed execution. Continue-As-New within the original chain remains allowed; it is not a second workload attempt. V03/V04 verify the pinned SDK/server behavior. Never terminate an existing workflow to satisfy repeated start.

Queue roles: `platform-control-<env>-v1` handles workflow tasks and DB/outbox lifecycle activities; `execution-provider-<target-pool>-v1` handles target-scoped provider activities. Initially the fake worker may poll both roles in the development namespace without Azure rights. Later separate ACA deployments/identities per BU production/nonproduction target pool. Queue names route work; isolation requires actual Temporal namespace/operation authorization and scoped Azure/DB permissions. Existing cross-platform workers are not evidence that production privileges are correctly isolated. [Temporal security](https://docs.temporal.io/self-hosted-guide/security).

Ordinary API callers receive no production Temporal certificate. Dispatcher may start/signal only the approved namespace/workflow operations; control/provider workers may poll/report only their approved namespace operations. If the deployed authorizer cannot distinguish queues, separate namespaces or accept only an explicitly approved same-trust worker group; queue naming is insufficient. Verify inspect-history, signal, reset, terminate, namespace-admin, and cross-namespace denial paths.

## Acceptance and dispatch protocol

1. API checks current identity/registry/policy, locks relevant concurrency admission rows and commits immutable spec, reserved execution slot, projection, idempotency response, event and start outbox together.
2. Dispatcher claims a due row using a short transaction (`FOR UPDATE SKIP LOCKED`) and expiring lease; no database lock spans a network call.
3. Dispatcher rechecks that the execution exists, matches the spec hash and is not already dispatched/terminal, then starts the stable workflow. A competing dispatcher may make the same start request; Temporal conflict handling plus DB state makes it harmless.
4. Persist delivery after confirmed start or an existing workflow with matching execution/spec/generation. A lost start acknowledgement is retried/reconciled as the same start, never with a new workflow ID.
5. Workflow startup reads cancellation/deadline/revocation state before provider submission. Persist first workflow-start evidence and run ID through an idempotent activity.

A delivered outbox flag alone is not proof a lifecycle is still running. A periodic reconciler checks accepted nonterminal records with stale progress against Temporal. If closed unexpectedly, create an operator/recovery ticket and reconcile provider state; do not start over as a new execution. If Temporal history is gone, a previously dispatched record is **never** treated as never-started. Persistent dispatch/attempt markers and provider discovery decide recovery. Catastrophic restoration uses the controlled recovery procedure below.

Cancellation commits its record, event and signal outbox in one transaction. If a signal arrives before workflow start, retain/retry the outbox; startup also reads current cancel intent. No Signal-With-Start path may bypass normal admission or recreate a completed execution. Persisted approval signals follow the same pattern only in later milestones.

Start-conflict validation compares the trusted DB admission/spec/generation binding with nonsecret immutable workflow Memo (`execution_id`, `spec_digest`, initial generation) and recorded workflow-chain identity obtained through Describe. Memo is not authorization and may only corroborate DB evidence. Mismatch or inability to prove correspondence creates a ticket; never acknowledge delivery merely because an ID exists. Generation advancement uses an idempotent signal containing the authorized recovery-record ID; an open workflow reloads that record before accepting the higher fence.

The control-worker reconciler owns never-started expirations/cancellation. Under the execution lock it closes the start outbox, advances the fence and sets `submission_closed`, then commits accepted → timed_out/cancelled as appropriate. Cancellation requires no-dispatch proof; if a start/submit is in flight or uncertain, it records the intent/ticket without asserting absence. An accepted record with no external attempts can complete no-allocation cleanup after the late-start path is fenced: any delayed workflow must reload the closed admission before effects. Release the existing reserved slot only with proven absence/closed attempts in the cleanup transaction; do not acquire another slot for reconciliation. `dispatch_status=pending` alone is insufficient proof.

Initial backlog settings: fail startup if maximum pending count, maximum oldest-pending age or execution deadline is unset. Before accepting, check count/oldest age transactionally with the admission reservation; caller quota returns 429, service backlog threshold returns 503, neither creates work. The reconciler checks expired records at a proposed 10-second cadence; delayed reconciliation remains visible and does not authorize allocating expired work. Live numerical thresholds and operator escalation age are V11 values.

Signal outbox delivery stops when the DB cancellation is acknowledged/superseded/failed or authoritative closed-workflow evidence has been classified. Closed with a known terminal outcome: mark superseded where appropriate and close the signal row atomically. Closed unexpectedly or history absent: close it as transferred to a durable recovery ticket, not delivered, and reconcile provider effects. Do not retry signals to a closed run indefinitely or use them to recreate the workflow.

## Activity effects and provider recovery

| Activity | Initial timeout/retry proposal | Effect/recovery requirement |
| --- | --- | --- |
| Load/check spec, write projection | Start-to-close 10s; schedule-to-close 60s; transient DB retries | Unique event/step IDs and revision/generation compare-and-swap |
| Validate capabilities | 15s / 60s; nonretryable invalid/policy failures | Pure inputs where possible; no allocation |
| Reconcile/submit | 20s / 120s; ambiguous outcomes always inspect first | Persist attempt and deterministic external IDs before call |
| Inspect/cancel/cleanup request | 20s / 120s; transient 429/5xx/transport backoff | No waiting for whole workload or deletion in one activity |
| Register/collect results | 20s / 120s per bounded page | Content digest + manifest ID upsert; resume from page/reference |
| Large approved object transfer if needed in M3 | Chunked ≤60s units, heartbeat 10s if a unit warrants it | Heartbeat offsets contain no credentials; delete/quarantine partial output |

Provider API retry backoff begins at 1s, doubles to a 15s cap, respects provider throttling guidance and remaining deadline. Bound the combination of SDK and Temporal retries; prefer minimal SDK retry budget so nested retries do not multiply. A timer resumes inspection after exhausted transient retries; a failed status call does not create another workload. Poll initially every 5s, increasing toward 30s while waiting for capacity; safe deterministic jitter derives from execution ID. Verify against provider quotas and recorded targets before finalizing.

The workflow handles activity errors explicitly. Exhausted transient DB/projection/result retries return to a durable timer/recovery branch using the same step/manifest IDs; they do not fall through to automatic workflow failure. At the lifecycle or delivery deadline, initiate independent stop/cleanup and transfer unfinished persistence/delivery to a ticket when storage becomes available. A permanent authorization/schema/invariant failure is not retried forever: stop further effects, preserve its origin, request cleanup and surface operator recovery. The sweeper reconciles from durable attempts/provider evidence if the workflow cannot write a ticket during a DB outage. V04 includes DB failure after observed success and result-registration exhaustion, not just failed provider reads.

Platform execution timeout is measured from accepted time. A provider task runtime ceiling and externally enforced maximum resource lifetime provide independent limits. Workflow execution timeout must allow the workload deadline plus cleanup budget and operational margin; it is not the primary timeout mechanism. Cleanup retries continue under a separate durable ticket if the main workflow closes or the service is down. Admission slots remain consumed while resource presence is unknown; release only after verified absence or approved accounting reconciliation, not merely a terminal workload result.

Use absolute UTC deadlines, not duration comparisons with different origins. Persist `deadline_at=accepted_at+timeout_seconds`; before each launch/inspection compute remaining time from that deadline. An observed provider runtime limit may end the workload earlier and is classified from its actual evidence; it cannot extend the platform deadline. Define cancellation deadline as section 3, cleanup deadline from first stop/terminal intent plus the approved cleanup budget, and maximum resource removal deadline from allocation plus its approved lifetime. Validate at dispatch that remaining lifecycle + cleanup + margin fits the resource cap; otherwise reject before allocation. Pass only remaining runtime to the provider. Temporal execution timeout is last-resort infrastructure protection beyond these budgets; tickets survive it. V08/V11 test ordering, clock skew and delayed allocation.

Actual workload retry count is **zero** for the POC. Batch `maxTaskRetryCount=0` controls nonzero-exit retries, not internal node-failure retries/rescheduling. Every supervisor invocation must consume a durable execution-once launch claim before starting any untrusted process, already in M2. Consumption is a one-way compare-and-swap bound to the verified assignment/spec; claim acknowledgement loss or supervisor death after consumption fails closed, even if the workload never launched. An in-process successful claim permits one spawn only; restarts cannot replay that authorization. Requeue/node replacement detection also triggers stop and recovery, but polling after requeue is not prevention. This deliberately trades availability for at-most-one launch; it is not exactly-once completion. [Batch retries](https://learn.microsoft.com/en-us/azure/batch/best-practices#design-for-retries-and-re-execution).

`ExternalAttempt` is persisted before each logical external mutation with deterministic account-relative pool/job/task IDs, spec hash and attempt token. Adapter `reconcile(execution_id, spec_digest)` discovers accepted work even if no provider reference was saved. Provider-level lookup absence after a timeout is not proof of rejection if consistency/processing remains uncertain. Reuse the **same** external identifiers only through a documented idempotent create/conflict path; compare existing immutable spec metadata and quarantine mismatches.

Critical deletion race: deletion must not erase the only duplicate-detection marker while a delayed submit can still succeed. Retain the provider job/marker or another durable admission tombstone until outstanding submit attempts have settled and the maximum request/retry window has elapsed. Persist `submission_closed` and reject any later submission activity before issuing an SDK call. New cleanup retries cannot reopen submission. Bound activity network deadlines; reconcile any late effects. If the chosen provider cannot fence/reconcile late submission after deletion, that is a failed provider conformance gate, not a cleanup success.

## Cancellation, fencing, and projection consistency

Use the public cancellation intent as a workflow message rather than immediately cancelling the Temporal workflow itself. It wakes inspection, requests provider termination, gathers bounded results, and runs explicit cleanup. Temporal administrative cancellation should enter a disconnected cleanup context when possible, but workflow termination/panic cannot be relied upon to execute cleanup. The independent sweeper is mandatory.

Only the active lifecycle generation may advance the primary projection. Activity retries use stable step IDs; event insertion and projection update occur in one DB transaction. Stale provider observations cannot regress state or overwrite a terminal outcome. A DB fencing token prevents competing reconciler writes; it does **not** fence an Azure API call already in flight. External deterministic IDs, durable attempts and late-effect reconciliation provide the other half. Do not declare exactly-once external effects based on a database lease or workflow ID. [Temporal idempotency guidance](https://temporal.io/blog/idempotency-and-durable-execution).

Sweeper leases target/execution tickets, enumerates only registered provider scopes, and compares tagged deterministic IDs with active/closed execution and attempt records. Unknown resources are quarantined for operator ownership review; delete only positively identified expired platform resources under the approved maximum-lifetime policy. A global sweeper identity across all subscriptions is not required; each target pool reconciles its own scope.

## Concrete failure timelines

| Failure point | Durable evidence left behind | Recovery and expected invariant |
| --- | --- | --- |
| DB commit succeeds, API response lost | Idempotency + execution + outbox | Retry returns original 202/ID; one admission reservation |
| DB commit succeeds, Temporal unavailable | Undelivered start row | Retry after recovery; status stays accepted/pending; deadline and backlog policy still apply |
| Temporal start succeeds, dispatcher dies | Existing stable workflow plus undelivered row | Retry receives conflict, validates identity, marks delivery; no second workflow |
| Provider accepts, response times out | Attempt + deterministic external IDs; reference may be absent | Discover same work; do not rerun workload on a fresh identity |
| Provider read fails during workload | Last observation + infrastructure unknown | Inspect after timer; workload retry remains zero |
| Worker dies after cancel acceptance | DB cancel intent + outbox | Startup reads intent even if signal was lost; reconcile provider stop |
| Blob upload succeeds, DB registration fails | Staged object with execution/manifest/digest | Register by digest on retry; orphan staging sweeper handles leftovers |
| Projection DB unavailable after provider success | Provider state and recorded attempt | Retried observation recovers; no blind workload rerun |
| Cleanup request accepted, response lost | Cleanup attempt + unresolved presence | Verify actual absence and access revocation; do not equate accepted delete with completion |
| Cleanup deadline expires | Failed cleanup + ticket + audit | Expose exception; continue target-scoped recovery |
| Old worker returns after lease takeover | Old generation/step ID | Reject stale projection write; inspect possible external effect |

## Replay, history, deployment, and recovery

The local SDK is pinned to Go SDK 1.48.0; the Compose Temporal CLI/dev-server image is 1.8.3, digest-pinned. Enterprise server/namespace versions remain **unknown**. `GetVersion` patching and retained legacy paths are implemented with selected real-history replay evidence. Continue-As-New is not yet proven. Do not adopt deprecated worker-versioning assignment-rule APIs. Worker Deployment Versioning is an optional follow-on after V03 confirms the server/SDK floors in [references](references.md), feature configuration and rollout/rollback tests. [Go workflow versioning](https://docs.temporal.io/develop/go/workflows/versioning).

Set history event/byte budgets below actual namespace limits. Initial guard: Continue-As-New when the SDK recommends it or measured history reaches the lower of 10,000 events and 50% of the configured event limit, or 50% of the configured byte limit. V04 measures events/bytes per poll including timers/activity retries, estimates `poll_count × measured events_per_cycle + signal/error margin`, and exercises a deliberately low guard. Carry execution/spec/generation, last sequence, cancel intent reference and original absolute deadlines; wait for handlers to finish and prevent losing queued cancellation before Continue-As-New. Keep cleanup tickets external. Never store log chunks or object bytes in history. Payload codec is a conditional extra control for permitted regulated references, not permission to store secrets.

Start with fixed warm replicas and bounded activity concurrency. On SIGTERM, make API readiness false, stop new claims/polls, allow short calls to finish, and persist ambiguous outcomes. Initial stop budget is 20s, to be tested against ACA's documented 30s shutdown behavior and actual deployed configuration. Do not depend on min replicas for process survival. [ACA lifecycle](https://learn.microsoft.com/en-us/azure/container-apps/application-lifecycle-management).

Recovery after cross-store restoration: freeze new dispatch and provider mutations, restore PostgreSQL to a separate endpoint, inventory Temporal open/closed workflows and target provider resources, and compare immutable admission/spec hashes and external attempts. Restore object versions/manifests, then rebuild projections. Quarantine provider/workflow evidence absent from the restored DB rather than resubmit it. Resume only reconciled records in a new fenced generation with original external identities and no new workload attempt. Test this procedure with deliberately unequal restore points; RPO/RTO proposals and ownership are in section 9.

An open workflow receives the approved generation via recovery signal and resumes inspection/cleanup only. A closed or absent workflow is recovered by leased DB tickets processed by the control reconciler and target provider worker; M1–M3 tickets are not new workflows. Neither path issues another Start for `execution/<id>` or resets a consumed launch claim. Restore comparisons include launch claims and spent identity assignments; missing durable launch proof means quarantine, never an assumed unused claim.
