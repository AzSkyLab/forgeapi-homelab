# AKS deployment base

Current as of: 2026-10-04 (work-day runbook added). Kustomize base for the engineer's hosting decision: Temporal runs on
an AKS cluster; this API and its Temporal worker run on the **same** AKS cluster as one
single-replica pod, because the SQLite operation ledger and saved Terraform plans must sit on
one local disk (see `docs/agent-architecture.md`, AGENTS.md). Validated with
`kubectl kustomize deploy/aks` and **rehearsed end to end on a local kind cluster** (below);
it has not been applied to AKS.

## What this is not

Not a Helm chart, not wired into CI, not an ArgoCD source yet. No image has been published to
back the placeholder below. Treat this as a reviewed starting point, not a verified deployment.

## Prerequisites

- An AKS cluster with [Microsoft Entra Workload ID](https://learn.microsoft.com/azure/aks/workload-identity-overview)
  enabled (the `azure-workload-identity` admission webhook running in-cluster).
- Temporal already deployed in-cluster (any namespace), reachable at a `host:port` you control.
- An Entra app registration (or user-assigned managed identity) with a federated credential for
  `system:serviceaccount:<your-namespace>:forgeapi`, holding whatever Azure RBAC role your
  patterns need (and the state storage account's Storage Blob Data Contributor, if you use
  remote state).
- A published `forgeapi` image (this repo's root `Dockerfile`) in a registry the cluster can pull.

## ConfigMap and Secrets the operator creates

Not generated by this base; create them in the same namespace before applying.

- `forgeapi-catalog` (ConfigMap, **required**), key `patterns.yaml`: the work pattern catalog
  (the image's built-in `patterns.yaml` is the lab's). Mounted at `/etc/forgeapi/catalog`.
  ```sh
  kubectl create configmap forgeapi-catalog --from-file=patterns.yaml=./patterns.yaml
  ```
- `forgeapi-temporal-tls` (Secret, only with Temporal TLS), keys `ca.pem`, `client.pem`,
  `client.key`, issued by the Temporal owners.

**Keep secret material off workstations.** The tenant mapping (it holds subscription IDs) and the
GitHub App key should come from Key Vault, not local files: enable the AKS Key Vault secrets
provider add-on (`az aks enable-addons --addons azure-keyvault-secrets-provider`) and use a
`SecretProviderClass` with `secretObjects` that syncs the Key Vault secrets into the Kubernetes
Secrets named below, authenticated with the same workload identity (the identity needs Key Vault
Secrets User). The `kubectl create secret` commands below are the equivalent for a lab.

- `forgeapi-tenants`, key `tenants.yaml`: the business-unit mapping text (`docs/tenancy.md`),
  consumed as `FORGEAPI_TENANTS_YAML`. Optional — omit for single-tenant (no placement/ownership).
  ```sh
  kubectl create secret generic forgeapi-tenants --from-file=tenants.yaml=./tenants.yaml
  ```
- `forgeapi-github-app`, keys `app-id`, `installation-id`, `private-key`: a GitHub App for
  reading private pattern repos, consumed as `FORGEAPI_GITHUB_APP_ID`,
  `FORGEAPI_GITHUB_APP_INSTALLATION_ID` and `FORGEAPI_GITHUB_APP_PRIVATE_KEY`. Optional — omit if
  all pattern repos are public. Both the `api` container (reading catalog metadata) and the
  `worker` container (`terraform init`) use it.
  ```sh
  kubectl create secret generic forgeapi-github-app \
    --from-literal=app-id=<id> --from-literal=installation-id=<id> \
    --from-file=private-key=./github-app.pem
  ```

Neither Secret is referenced by name anywhere except the StatefulSet's `secretKeyRef`s, and both
are marked `optional: true` so the pod still starts without them.

## Apply

```sh
kubectl create namespace forgeapi   # or your own namespace
kubectl apply -k deploy/aks -n forgeapi
kubectl -n forgeapi rollout status statefulset/forgeapi
```

## Verify

```sh
kubectl -n forgeapi port-forward svc/forgeapi 8000:80
curl -fsS http://127.0.0.1:8000/readyz   # {"status":"ready","checks":{"ledger":"ok","temporal":"ok"}}
curl -fsS http://127.0.0.1:8000/healthz  # {"status":"ok","contract":"agent-v1"}
```

`/readyz` fails closed if either the local ledger or Temporal is unreachable; it never mutates
anything. Beyond this, no end-to-end deploy/apply has been run against a real AKS cluster from
this change.

## Work-day runbook

The order to follow on the work cluster. Steps marked **(lab-proven)** ran on 2026-10-04 in a
kind rehearsal of this exact base with a real Entra tenant (see below); the rest can only be
proven at work. Stop at the first failure and record it in `docs/progress.md`.

1. **Caller app registration** (the API's audience). Expose an API scope, set
   `groupMembershipClaims: SecurityGroup` and, if users are in many groups, emit only groups
   assigned to the application (a token with group overage is refused). Note its tenant ID and
   application (client) ID for `FORGEAPI_ENTRA_TENANT_ID` / `FORGEAPI_ENTRA_AUDIENCE`. The API
   accepts **v2 tokens only** (issuer `https://login.microsoftonline.com/<tenant>/v2.0`, audience
   = the client-ID GUID): set `api.requestedAccessTokenVersion` to `2` in the manifest; a
   registration reused from the Easy Auth version probably issues v1 tokens and every call would
   get 401. Set an Application ID URI (`api://<client-id>`) and, so people can get a token with
   `az account get-access-token --resource api://<client-id>`, pre-authorize the Azure CLI
   (`04b07795-8ddb-461a-bbee-02f9e1bf7b46`) for the scope; agents use their own client
   registration with that scope. The portal (`/console`) takes the same token pasted in.
   **(lab-proven:** v2 tokens with a `groups` claim validate in the pod; the lab registration had
   exactly these settings.)
2. **Worker identity.** A user-assigned managed identity (or app registration) with a federated
   credential: issuer = `az aks show -g <rg> -n <cluster> --query oidcIssuerProfile.issuerUrl -o tsv`,
   subject = `system:serviceaccount:<namespace>:forgeapi`, audience `api://AzureADTokenExchange`.
   Grant it only the Azure RBAC roles the registered patterns need on the target subscriptions
   (plus Storage Blob Data Contributor on the state account if `FORGEAPI_STATE_*` is set). For
   `FORGEAPI_LIVE_GROUP_CHECKS`, also Microsoft Graph `GroupMember.Read.All` (application, admin
   consent). **(Not provable in the lab:** the token exchange with real Entra; the provider side
   is proven against Floci.)
3. **Image.** The engineer pushes tag `v1.0.0` (it must equal `v` + `project.version` in
   `pyproject.toml`, which the workflow checks) to the GitHub repository that holds this code;
   `.github/workflows/image.yml` runs the checks and publishes `ghcr.io/<owner>/forgeapi:v1.0.0`
   with SBOM and provenance. Import it into the work registry (`az acr import --name <acr>
   --source ghcr.io/<owner>/forgeapi:v1.0.0`, with `--username/--password` if the package is
   private) and set `images[].newName` to the ACR name and `digest: sha256:...` (instead of
   `newTag`) in `kustomization.yaml`. The cluster must be allowed to pull from that ACR.
3a. **Temporal.** Ask the Temporal owners for: the frontend address, a namespace registered for
   ForgeAPI (set `FORGEAPI_TEMPORAL_NAMESPACE`), whether TLS/mTLS is required (then the CA and a
   client certificate as the `forgeapi-temporal-tls` Secret), and the frontend port if not 7233
   (the NetworkPolicy allows 7233).
3b. **Ingress.** The base has only a ClusterIP Service and admits one client namespace on port
   8000. Decide how callers reach it (an internal ingress controller's namespace in the
   NetworkPolicy, with TLS terminated there), or start with `kubectl port-forward` for
   verification only.
4. **Placeholders and Secrets** as listed above. Tenant mapping as the `forgeapi-tenants`
   Secret **(lab-proven)**, the catalog as the `forgeapi-catalog` ConfigMap (lab-proven), remote
   state settings if patterns use the azurerm backend. Optional Temporal TLS: uncomment the
   `temporal-tls` volume/mounts and set `FORGEAPI_TEMPORAL_TLS*` (settings proven in a real
   handshake, not with your Temporal).
5. **Apply** and wait for `rollout status`; the pod must show every container Ready with 0
   restarts **(lab-proven)**. Then check the configuration inside the pod (no file leaves it):
   `kubectl exec forgeapi-0 -c api -- sh -c 'printenv FORGEAPI_TENANTS_YAML > /tmp/t.yaml &&
   python -m app.team_check /tmp/t.yaml --catalog "$FORGEAPI_CATALOG_PATH"; rm /tmp/t.yaml'`
   (exit 0), and for each pattern `GET /v1/patterns/{name}/check?version=<tag>` with a caller
   token (the API fetches private repos with the GitHub App; the `pattern_check` CLI does not use
   credentials).
6. **Verify, in this order** (port-forward or your client namespace; use a real caller token,
   e.g. `az account get-access-token --resource api://<audience-app-id>`):
   - `/readyz` 200 (ledger ok, temporal ok);
   - `GET /v1/agent` with no token → 401, with a garbage token → 401, with a token for another
     resource (`--resource https://management.azure.com/`) → 401 **(lab-proven)**;
   - with the caller token: discovery lists only the business units the caller's groups grant;
     validate/submit into a unit or environment the caller lacks → 403 **(lab-proven)**;
   - deploy the cheapest registered pattern in a dev zone: plan → review `changes` → execute the
     exact `plan_digest` → `succeeded`; read the resource back in the Azure portal or CLI;
     resource shows `owned_by_caller: true` and no subscription ID **(lab-proven on an emulator)**;
   - `POST /v1/resources/{id}/drift-check` → `in_sync`; destroy intent → plan → execute → gone;
   - `kubectl logs` for `api` and `worker` contain no bearer tokens **(lab-proven)**.
7. **Record** the image digest, operation IDs and readbacks in `docs/progress.md`; update
   `docs/work-deployment.md` (what is now proven at work).

Rollback: scale the StatefulSet to 0 (the disk and ledger stay), redeploy the previous image
digest, scale back to 1. Pending `planned` operations made by a different Terraform version
fail safely and must be resubmitted; never edit the ledger or force-unlock state.

## Single-replica: what it means

`replicas: 1` is load-bearing, not a placeholder: the API and worker share one managed-disk
volume (`volumeClaimTemplates: data`, `ReadWriteOnce`), so a second replica would need a second
disk this milestone doesn't support. `RollingUpdate` with `podManagementPolicy: OrderedReady`
still applies, which means every rollout (new image, changed config) briefly takes the API and
worker down -- the old pod terminates before the new one reaches Ready. There is no hot standby.
Plan upgrades around that; it is not a bug to fix later in this base.

## Identity

The pod authenticates to Azure via [AKS workload identity](https://learn.microsoft.com/azure/aks/workload-identity-overview)
only (`FORGEAPI_AZURE_USE_AKS_WORKLOAD_IDENTITY=true`): no certificate, no managed-identity MSI
shim, no client secret. `automountServiceAccountToken` is left at its default (`true`) on
purpose -- the workload-identity webhook's federated-token projection rides alongside the normal
service-account token projection, and setting it `false` would suppress that too.

## Read-only root filesystem

Every container runs `readOnlyRootFilesystem: true`. Checked against this repo's `Dockerfile`
and `app/worker.py`:

- `HOME=/tmp` is baked into the image; an `emptyDir` is mounted at `/tmp` for it and for any
  Terraform/git scratch files.
- `uv` only runs during `docker build` (`uv sync --frozen --no-dev`); the running containers
  invoke `uvicorn`/`python` directly, so no uv cache needs to be writable at runtime.
- The Terraform plugin cache and all per-deployment workspaces live under `FORGEAPI_DATA_DIR`
  (`app/terraform.py`: `deployment_dir`, `_env`'s `TF_PLUGIN_CACHE_DIR`), which is the `/data`
  PVC, not `/tmp`.
- Python may be unable to write `.pyc` bytecode caches next to the read-only application code;
  this only costs import speed, it is not fatal (CPython silently skips an unwritable cache).

If a future pattern or dependency needs another writable path, add another `emptyDir` rather
than loosening `readOnlyRootFilesystem`.

## Network policy

Ingress is restricted to TCP/8000 from `<CLIENT_NAMESPACE_PLACEHOLDER>` only. Egress is
restricted to DNS (53), the Temporal namespace (7233) and HTTPS (443) generally -- Terraform
providers, Entra token endpoints and GitHub are all reached over HTTPS to addresses that are not
stable or enumerable from here, so 443 egress is not narrowed further in this base. Narrow it
with your platform's own egress tooling if you need to.

## Not covered / not verified

- No image has been built and pushed for this base; the registry reference is a placeholder.
- No apply, rollout or `/readyz` check has been run against a real AKS cluster.
- Workload identity: the platform side (webhook variables → azurerm's federated-token path, provider
  and backend) is proven against the Floci Azure emulator on Terraform 1.15.9 and 1.16.5
  (`tests/test_floci_workload_identity.py`); the real webhook, federated credential and RBAC are not.
- Azure RBAC role assignments for the app registration/identity are the operator's
  responsibility; none are created here.
- Remote Terraform state (`FORGEAPI_STATE_*`) is not configured in this base; add it to the
  ConfigMap if your patterns declare `backend "azurerm" {}`.
- Temporal TLS is off by default in `configmap.yaml` (commented example included); turning it on
  needs the PEM files mounted into the pod (e.g. from a Secret) at the paths you configure.
  The settings themselves are proven in a real TLS/mTLS handshake against a real Temporal server
  (`tests/test_temporal_tls_live.py`), not yet against your cluster's Temporal.
- Pod disruption budgets, horizontal scaling and multi-replica/multi-disk designs are explicitly
  out of scope for this milestone (AGENTS.md "Keep it small").

## Local rehearsal (kind, no cloud)

`deploy/aks-rehearsal/` applies this exact base to a throwaway cluster with a locally built
image, the cluster's default storage class, `FORGEAPI_AUTH_MODE=none`, the example `local-file`
pattern, and the NetworkPolicy placeholders filled (`forgeapi-clients`, `temporal`).
`temporal-dev.yaml` there runs a Temporal dev server at the address the base expects.

```sh
kind create cluster --name forgeapi-rehearsal
docker build -t forgeapi:rehearsal . && kind load docker-image forgeapi:rehearsal --name forgeapi-rehearsal
kubectl apply -f deploy/aks-rehearsal/temporal-dev.yaml
kubectl create namespace forgeapi && kubectl apply -k deploy/aks-rehearsal
kubectl -n forgeapi rollout status statefulset/forgeapi
kubectl -n forgeapi port-forward svc/forgeapi 18080:80   # then plan/apply through the API
```

Result (2026-10-04, kind v0.30.0 / Kubernetes 1.34, image built from this tree): pod `2/2`
Ready (`/readyz` ledger ok, temporal ok); a `local-file` plan → digest approval → apply ran
through the pod with read-only root filesystems, non-root uid 1000 and `fsGroup` 1000, and the
file read back from the volume; a plan saved before `kubectl delete pod` kept the same digest on
the recreated pod and applied after the restart; both resources destroyed. A second home-lab run used the Floci emulators as the cloud: three sidecars forwarded
`localhost:4566/4577/4588` to the emulators, the emulator storage proxy ran as a sidecar, the
emulator CA was added to the worker's trust bundle, and a tenant mapping placed Azure, AWS and GCP.
The first attempt was correctly **blocked by this base's NetworkPolicy** (kind v0.30's CNI
enforces policies; the base allows egress only to DNS, Temporal and TCP 443, and the emulators
listen elsewhere); after adding an egress rule for the emulator ports in the rehearsal overlay,
the pod planned, applied and destroyed an Azure resource group + storage account + container,
an S3 bucket and a GCS bucket (emulator readbacks 200, then 404), ran a drift check, and an
`uncertain` apply from the blocked attempt was resolved through the operator reconcile path.
Not proven in these two runs: Entra auth (see the third run below), workload identity with real Entra, Azure Disk (`managed-csi`) and real Azure.

A third, work-like run (2026-10-04) applied this base with the ConfigMap **as shipped**
(`FORGEAPI_AUTH_MODE=entra`; only the tenant, audience and Temporal address filled in), an image
built from `main`, the tenant mapping as the `forgeapi-tenants` Secret keyed by real lab Entra
group IDs, and Floci AWS as the cloud. Through the pod: `/readyz` 200; no token, a garbage token
and a real tenant token for Azure Resource Manager → 401; the real caller token (fetched JWKS from
`login.microsoftonline.com` through the NetworkPolicy's 443 egress) → only the caller's business
unit; another unit → 403; an S3 bucket planned, applied by exact digest (404 → 200), owned by the
caller, no account ID shown, destroyed (404). No bearer token text in the `api` or `worker` logs;
0 restarts. Cluster, emulator and `kind` network removed afterwards.
